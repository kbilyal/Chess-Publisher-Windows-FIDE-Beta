1. Managed-file checkpoint failure cause
----------------------------------------
The forced save path called fileSaveTournament(true), which first called saveAll().
saveAll() called saveData(), and saveData() wrote the current tournament snapshot to
browser localStorage before the managed-file checkpoint had been proven durable.
cpExecutePersistentSave() also updated browser recovery storage before the managed
LocalEngine/native tournament file write.

Thus browser recovery was incorrectly coupled to forced durability. A localStorage
quota/storage failure could contaminate the checkpoint outcome even though browser
storage is only secondary recovery.

Fix:
- forced save synchronizes UI -> memory with browser persistence suppressed during capture;
- managed LocalEngine/native file is written first;
- failure of all managed-file targets => checkpoint FAIL and no Cloud write;
- after managed-file success, IndexedDB recovery is attempted first;
- localStorage recovery is best-effort; quota failure is warning-only.

Answer: YES — localStorage/browser recovery was previously too tightly coupled to the
forced durability path. It is no longer accepted as proof of a successful Desktop checkpoint.

2. Fingerprint schema
---------------------
Old Desktop: legacy/implicit content-fingerprint contract without a valid persisted
fingerprintContentSchema gate on stored base hashes.
New Desktop: fingerprintContentSchema = 7, matching current Web reference projection.

Schema-7 behavior:
- recursive volatile-key filtering;
- installation-secret sanitization preserved;
- cloud/online/hub/publication/savedAt/dgt/uiState/runtimeState excluded;
- telegram.token and telegram.botToken excluded;
- recursively sorted object keys; array order preserved;
- old/missing-schema base hashes are ignored and reconstructed from baseRevision;
- remoteRevision == baseRevision can safely use current remote content as the common base.

3. Three-way / recovery behavior
--------------------------------
Local == Remote -> NO-OP / repair common base.
Local == Base and Remote != Base -> CLOUD_ONLY / Pull.
Local != Base and Remote == Base -> DESKTOP_ONLY / Push.
Local != Base and Remote != Base and Local != Remote -> BOTH_CHANGED / fail closed.

After successful Desktop -> Cloud upload, server response cloudTournamentId, internalId,
revision and contentFingerprint become the new common base and are durably saved. An
immediate second SYNC with no edits is NO-OP. Equal-content recovery repairs stale base
metadata after a previous post-upload local metadata-save failure.
